# Lineage II C3 NWindow.dll — source rebuilt in C++

[Português](README.md) · **English** · [Русский](README.ru.md)

A function-by-function rebuild of the `NWindow.dll` of the Lineage II **Chronicle 3 (Rise of Darkness)** client:
the native UI DLL (windows, controls, NPC HTML, IME, chat, console, messenger, replay). The target is the build of
15/09/2005 (TimeDateStamp `0x4329071F`, Visual C++ 7.0 13.00.9466, md5 `f0362880…`, 309 classes, 311 exports,
10,992 functions). The same source builds two ways:

| CMake target | Output | What it is |
|---|---|---|
| `NWindowDecomp` | `build/bin/Release/NWindowDecomp.dll` | **hook mode**: runs next to the stock `NWindow.dll` and replaces every function already rebuilt with a `jmp` to ours |
| `NWindowStandalone` | `build/standalone/Release/NWindow.dll` | **standalone**: the whole `NWindow.dll`, our code only, loaded by the game in place of the stock one |

It is the third project of a series: it was forked from the C2 project (itself forked from the C1 one), with the
same tools and method aimed at the C3 binary; the C2 source was ported to C3 and verified function by function.

## How it works

**Hook mode.** The installer (`tools/install_test.py`) adds an import of `NWindowDecomp.dll` to the stock
`NWindow.dll`. It loads before any stock code runs and puts a `jmp` at the entry of every function we have rebuilt
(an `NW_HOOK_*` next to each definition, `src/re/NwHook.h`). The rest stays stock code. So each new function is
tested in the real game, and any of them can be switched off in `NWindowDecomp.ini` (`[Hooks] Disable=`) to
isolate a bug.

**Standalone (phase 5).** With `NW_HOOK_MODE=0` the hook macros are empty and the source builds `NWindow.dll` on
its own: the 309 `UClass`es (`src/standalone/Classes.gen.cpp`), the globals (`NwGlobals.cpp`, generated from the
C3 image), the exports with the stock ordinals (`src/standalone/NWindow.def`) and the 7 colour cursors. The engine
(`Core.dll`/`Engine.dll`) loads our DLL the way it loaded the stock one. **GameGuard** (`NPG*`, the nProtect static
library the stock image carries) is not ported: in the standalone it is a documented no-op
(`include/nwindow/NGameGuard.h`, `src/standalone/NwGameGuard.cpp`), and the engine's GameGuard query to the console
gets an answer (zeros, without GameMon) so the login goes on (`NConsoleWnd::GameGuardQueryX`,
`src/nwindow/NConsoleWndC2.cpp`; details in [docs/notas/C3_Standalone.md](docs/notas/C3_Standalone.md), section 2c).
NKeyCrypt (`npkcrypt.dll`) is real code, loaded by ordinal.

There is no new-feature layer (phase 6) in C3: the `#if NW_FEATURES` blocks in the source are call sites inherited
from C1 and inert (no target defines `NW_FEATURES` and their headers are not in this tree). See
[docs/MODIFY_INTERFACE.md](docs/MODIFY_INTERFACE.md) for how to add one.

## Status

- Hook mode: **4,970 of 6,534** functions to rebuild are done (**93.03 %** of the code bytes). The 87 left without
  a reason are GameGuard (84 `NPG*` + 3 anonymous ones of the same library), out of scope by the owner's decision;
  the other unhooked ones are generated by the compiler in the standalone (scalar deleting destructors,
  `InternalConstructor`, static initialisation). The 4,970-hook build was tested in the game by the owner
  (18/10/2026). Live count: [docs/PROGRESSO.md](docs/PROGRESSO.md) (generated by `tools/build_db.py`).
- Hook-mode judges in the last cycle: `hooks 4970/4970, 0 errors`, 4,738 ok + 232 explained, 0 unexplained,
  `regcheck` 0 problems, `CHECKS: ALL OK`.
- Standalone (finished on 29–30/10/2026): links with 0 unresolved symbols (2,198,016 bytes), passes
  `verify_standalone.py` (PE, imports, resources, 315 exports, 310 classes, vtables) and `smoke_standalone.py` (the
  same 438 output lines as the stock DLL) and **loads in the game** in place of the stock one.
- The messenger (MSN) is fully ported but only structurally proven (judges + reading the assembly): there is no
  messenger server to test against.
- The technical notes (`docs/`) are in Portuguese (a few in English); code comments are in English.

## Requirements

- Windows, **Visual Studio 2022** with C++ for x86 (MSVC v143), **CMake ≥ 3.20**;
- **Python 3** with `pefile` and `capstone` (`pip install pefile capstone`): used by the standalone build (cursor
  extraction) and by every tool; `unicorn` (`pip install unicorn`) for the differential tests in `tools/port/emu/`;
- **your own Lineage II C3 client**. No game file is in the repository: copy into `orig/` the files listed in
  [orig/README.md](orig/README.md) (the `NWindow.dll` must have the md5 given there);
- for the judges of the full cycle (`verify_hooks.py`, `regcheck.py`, `verify_standalone.py`, `build_db.py`,
  `tools/port/*`): the Ghidra export in `analysis/ghidra/`, recreated by `bash tools/ghidra/run_full.sh` (Ghidra
  11.3.2 and JDK 21; paths in the `NWD_GHIDRA_HOME` and `GHIDRA_JAVA_HOME` variables).

## Build

In an x86 *Developer Command Prompt* of VS 2022 (or after `vcvars32.bat`), at the repository root:

```bat
cmake -S . -B build -A Win32 -DNWD_GAME_SOURCES=ON
cmake --build build --config Release
cmake --build build --config Release --target NWindowStandalone
```

`-DNWD_GAME_SOURCES=ON` compiles the game source (`src/nwindow`); without it (the historical default, `OFF`) only
the hook runtime (`src/re`) is built, no function is replaced and the standalone does not link. The first `--build`
makes the hook-mode DLL and the test tools (`nwd_smoke`, `nwd_difftest`) and does not need `orig/`.
`NWindowStandalone` needs `orig/NWindow.dll`. The `NWindowStandaloneProbe` target (linked with
`/FORCE:UNRESOLVED`) is a diagnostic only and must **never** be loaded.

## Install and test

Use a **copy** of the client's `system` folder (e.g. `system_nwtest`), never the one you play from.

**Hook mode:**

```bat
python tools\install_test.py --system "<C3 client>\system_nwtest"
python tools\install_test.py --system "<C3 client>\system_nwtest" --restore
```

The first writes an `NWindow.dll` rebuilt from `orig/NWindow.dll` with the extra import, `NWindowDecomp.dll` and an
`NWindowDecomp.ini` (the `NWindow.dll` that was there is kept as `NWindow.dll.pre-decomp-bak`); the second puts
back what was there. `NWindowDecomp.log` in that folder lists every installed hook. In the `.ini`:
`[Hooks] Enabled=0` keeps all the stock code; `Disable=` takes an address (`1000cc40`), a method
(`NCGDevice::DrawText`) or a class (`NCGDevice::*`); `[Debug] Marker=1` draws marks only our code draws (a yellow
line at the top, `#` in the password, a red caret) to check that the hooks are live. `python tools\hook_ini.py`
writes that `.ini` (see `--help`).

**Standalone:** close the game, return the test folder to stock (`install_test.py --restore`), keep its
`NWindow.dll` aside and copy `build\standalone\Release\NWindow.dll` over it. That file only: no `.ini` or `.log`
next to it (the client's `npkcrypt.dll` stays in the folder). To go back, put the stock one back.

**Full cycle** (build, smoke, judges, standalone, install, database refresh; stops at the first failing step):

```bat
python tools\cycle.py --system "<C3 client>\system_nwtest" --game-source --standalone
python tools\cycle.py --system "<C3 client>\system_nwtest" --game-source --standalone --no-install
```

The cycle uses `build/` and copies from the `--system` folder the DLLs the loader needs (`Core.dll`, `Engine.dll`
and their dependencies) into `build/smoke_system`. The game in that folder must be closed for the install step.
`tools\port\cycle.bat` runs the cycle with `--game-source --no-install` and then the port judges
(`verify_data.py`, `check_breakers.py`, `checks.py`); it reads the test folder from `NWD_CLIENT_SYSTEM`.

**Machine paths.** No tool contains a path of the author's machine: a folder outside the repository comes from the
command-line option or from one of these variables (the option wins; a tool that needs one and has none stops and
says which):

| Variable | Points to | Used by |
|---|---|---|
| `NWD_CLIENT_SYSTEM` | the test client's `system` folder (a copy: the install writes into it) | default `--system` of `install_test.py`, `cycle.py`, `smoke_standalone.py`, `difftest.py`; `hook_ini.py`; default `--log` of `verify_hooks.py` and `tools/port/verify_args.py`; `Engine.u`/`Core.u` of `ue2_layouts.py` |
| `NWD_STOCK_SYSTEM` | (optional) the `system` folder you play from | `install_test.py` refuses to write into it |
| `NWD_GHIDRA_HOME` | the Ghidra install (with `support/analyzeHeadless.bat`; `GHIDRA` still takes precedence); `GHIDRA_JAVA_HOME` = the JDK 21 | `tools/ghidra/*.sh`, `tools/c2/ghidra_census.sh` |
| `NWD_C2_ROOT` | a checkout of the C2 project (the port's base tree; the older name `NW_C1_ROOT` works too) | the `tools/port/*` tools that compare with the base (`gen.py`, `match.py`, `layout.py`, `eligible.py`...) |
| `NWD_C1_ROOT` | a checkout of the C1 project (with its `orig/`) | `tools/c2/compare_nwindow.py`, `ue2_console_slots.py`, `ue2_gamedata_regions.py`, `ue2_ret_diff.py`, `ue2_vtable_diff.py` |
| `NWD_C2_SYSTEM` | the `system` folder of a C2 client | `tools/c2/packet_formats.py` |
| `NWD_C1_SERVER` | the deploy folder of a C1 server (pages in `gameserver/data/html-en`) | `difftest.py`, page set `server` (skipped without it) |

## The judges

The cycle (`tools/cycle.py`) runs these, in this order; "green" means the cycle exits with code 0.

| Judge | Command | What it proves |
|---|---|---|
| smoke | `build\smoke\Release\nwd_smoke.exe build\smoke_system` | the patched `NWindow.dll` loads outside the game and every hook reports `ok` (`NWindowDecomp.log`) |
| verify | `python tools/verify_hooks.py --log build/smoke_system/NWindowDecomp.log` | each of our functions against the stock one in the assembly: bytes popped at `ret`, vtable slots and imports called; a difference passes only with an explanation in `db/verify_notes.csv` |
| regcheck | `python tools/regcheck.py --game-src` | no stock caller relies on a register our function may change (the stock image was built with `/GL`) |
| standalone: declarations | `python tools/verify_standalone.py --checks source` | our `NW_DECLARE_CLASS` / `NW_CHECK_VTABLE` against the stock class table |
| standalone: verify | `python tools/verify_standalone.py --dll build/standalone/Release/NWindow.dll` | PE, imports, resources, exports, classes and vtables equal to the stock ones, without running it (accepted differences in `tests/standalone/notes.csv`) |
| standalone: smoke | `python tools/smoke_standalone.py --dll build/standalone/Release/NWindow.dll` | loaded the way the engine loads it: 309 classes registered, output equal to the stock DLL's |
| db | `python tools/build_db.py --game-src` | regenerates `db/functions.csv` and `docs/PROGRESSO.md` |

Port judges (`tools\port\cycle.bat`, after the cycle): `tools/port/verify_data.py` (the constants, field
displacements, strings and globals each function touches; notes in `db/verify_data_notes.csv`),
`tools/port/check_breakers.py` (no hook reaches an `NW_UNPORTED`) and `tools/port/checks.py` (return values,
constant arguments, stack frames, sizes, CRT: prints `CHECKS: ALL OK`). The differential tests under unicorn
(`tools/port/emu/t_*.py`) run the stock function and ours side by side. `difftest.py` (`tests/golden/`) still has
the C1 cases and refuses to run on the C3 image (the cycle's `--difftest` stays off).

## Layout

```
orig/          your client's binaries (not in git; md5 in orig/README.md)
analysis/      facts extracted from the stock binary (classes, EH, vtables; the exported Core/Engine vtables; the
               Engine.u/Core.u layouts; packet formats of the C3 Engine.dll); analysis/c2/ = the same data for C2
               (the port's base); analysis/ghidra/ = Ghidra export (generated, not in git)
db/            function database (functions.csv is generated) + hand-written names, notes and checks; db/c1/, db/c2/ = reference
include/ue2/   declarations of the C3 Core.dll/Engine.dll, checked against the exports
include/nwindow/, src/nwindow/    the decompiled source, one class per file
src/re/        hook-mode runtime (hook installer, log, ini, CRT compatibility)
src/standalone/                   IMPLEMENT_CLASS / IMPLEMENT_PACKAGE, globals, GameGuard no-op, NWindow.def
tests/         reference outputs (golden) and the standalone lists/notes
third_party/ue_import/            .def of the Core/Engine exports (turned into .lib at build time)
tools/         analysis, generation, install, judges, cycle; tools/port/ = the C2 -> C3 port and its judges;
               tools/c3/ = packet formats of the C3 client; tools/c2/ = tools inherited from C2
docs/          plan, conventions, progress and technical notes
```
